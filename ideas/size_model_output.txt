-------------------------------------------------------------
  Higher rank at lower delta precision keeps more capacity for the same GB.
   rank  kept params   %cap         bf16        int8        int4

    128      213.7 B  7.85%       484 GB        270 GB        164 GB*
    256      424.4 B 15.59%       906 GB        481 GB        269 GB 
  * fits the target. Delta precision is a second lever independent of rank:
    rank 128 @ int4 keeps 4x the capacity of rank 32 @ int8 for similar GB.

PER-TOKEN I/O AND COMPUTE -- the reason Option A is not just a size win
-----------------------------------------------------------------------
  today: 1,472 expert reads x 17.55 MB = 25.83 GB read per token
         (matches the measured 25.83 GB/token in docs/data/memory-ladder.tsv)

  With a shared base, Base@x is IDENTICAL for all 16 routed experts in a
  layer, so it is computed ONCE per layer, not 16 times:
    sum_e g_e (Base + U_e V_e^T) x  =  Base@x + sum_e g_e U_e (V_e^T x)

  bases at int8 = 3.04 GB -- small enough to stay RESIDENT
    rank  16: delta  319.5 KB/expert ->  0.47 GB/token read ( 54.9x less I/O), expert MACs 12.2x less
    rank  32: delta  639.0 KB/expert ->  0.94 GB/token read ( 27.5x less I/O), expert MACs  9.9x less
    rank  64: delta 1278.0 KB/expert ->  1.88 GB/token read ( 13.7x less I/O), expert MACs  7.1x less

  So Option A attacks the 200 GB target AND the 25.83 GB/token bottleneck
  with the same change. That is the only idea here that does both.
